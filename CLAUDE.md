## Как работать с заказчиком (обязательно)

- Говорить по-русски. Заказчик — Моше, не разработчик, но точно выполняет пошаговые инструкции.
- Всё, что требует его действий (регистрации, ключи, настройки), — по одному шагу, коротко, с названиями кнопок.
  Интерфейсы сервисов меняются: если кнопки нет, просить снимок экрана, а не гадать дальше.
- **Никогда не просить присылать в чат пароли, секретные ключи и токены.** Секреты кладёт он сам:
  в Vercel (Settings → Environments → Production → Environment Variables) или в `.env.local`.
- Перед любой платной операцией: что именно, сколько стоит (сверить на официальной странице) — и ждать «да».
- Работать по этапам из раздела 13 ТЗ. После этапа — рабочая версия на Vercel и список, что проверить.
- Проверять свою работу (сборка, страницы в браузере, данные в базе), а не считать задачу готовой по факту написания кода.
- Если в ТЗ чего-то не хватает или есть противоречие — сказать до начала работы, не додумывать молча.
- Любое изменение требований вносить в ТЗ.

## Переменные окружения

Открытые значения (адрес Supabase, publishable key, имя бота) зашиты в `src/lib/env.ts` как значения по умолчанию:
Vercel не дал заказчику сохранить имена с `NEXT_PUBLIC_`. Переменные `NEXT_PUBLIC_*` их переопределяют, если появятся.

Секреты (в Vercel, окружение Production):
- `SUPABASE_SECRET_KEY` — секретный ключ Supabase `sb_secret_…` (не publishable! код это проверяет).
- `TELEGRAM_BOT_TOKEN` — токен бота от @BotFather. Из него же выводится секрет вебхука (`webhookSecret`), отдельной переменной нет.
- `CRON_SECRET` — необязательно; если задан, `/api/cron/daily` принимает только вызовы Vercel Cron.

Полный список с пояснениями — `.env.example`.

## Архитектура и подводные камни

- **Next.js 16.4** (новее данных обучения модели). Перед кодом читать `node_modules/next/dist/docs/` (см. `AGENTS.md`).
  `middleware` теперь `proxy` (`src/proxy.ts`). `params`/`searchParams` — Promise.
- `cacheComponents: true`: чтение cookie/searchParams только внутри `<Suspense>`; данные кэшируются через `'use cache'`
  с тегами (`dictionaries`). `partialPrefetching: false` — чтобы неизвестная карточка отдавала честный 404 (SEO).
  `generateStaticParams` обязан вернуть хотя бы один элемент.
- Публичные страницы статичны: состояние входа в шапке читается в браузере (`UserMenu`), proxy работает только на
  `/profil`, `/kabinet`, `/admin`, `/vhod`, `/auth`, `/api`.
- Адреса: `/<раздел>/<slug>` — категория **или** карточка; база не даёт им совпасть (триггер `check_slug_namespace`).
  Второй уровень — подкатегория или район. Старые адреса карточек — `listing_slug_history` (для 301).
- Карточка = `listings` + версии `listing_versions` (данные блоков в JSON). Типы блоков — `src/lib/blocks/types.ts`.
  Публикация — SQL `publish_listing_version(version)`: переносит данные в поисковые поля `listings` (`refresh_listing_search`).
  **`listings.features` (jsonb) — включённые платные функции; особенности заведения — `listings.amenities` (text[]).**
  Поиск — SQL `search_listings(...)`; псевдонимы районов/категорий — колонки `aliases`, синонимы — `search_synonyms`.
  Категория из адреса (`p_category`) фильтрует строго (с подкатегориями); слово категории во фразе только поднимает
  её карточки выше (их и так находит текст: название и псевдонимы категории попадают в `search_tsv`).
  **После правки псевдонимов категорий нужно вызвать `refresh_listing_search` для карточек этих категорий.**
  Страница категории: «По районам» — свёрнутый `<details>`, только районы с карточками (SQL `category_district_counts`).
  Шапка на компьютере: поиск `flex-1 min-w-40` сжимается первым; «Админка»/«Мои карточки» с `lg`, имя профиля с `xl`.
  Подкатегория: `categories.parent_id`, адрес `/<раздел>/<категория>/<подкатегория>`; `/<раздел>/<подкатегория>` → 301.
  Данные каталога кэшируются с тегом `listings`: после публикации/правки нужно сбрасывать (`revalidateTag`).
- **Фильтры по категориям (2 ноября 2026, вариант Б аудита):** таблица `src/lib/catalog/filter-config.ts` (какие фильтры
  и с какими подписями в категории; исключения подкатегорий — ветеринария без кассы, логопеды с кассой), данные —
  SQL `category_filter_stats(section, category_id)`, сборка — `getFilterAvailability` (`src/lib/data/filters.ts`):
  фильтр виден, если он есть в таблице И хотя бы одна карточка подходит; выбранный фильтр виден всегда.
  Новая категория верхнего уровня = строка в `BY_CATEGORY` (иначе общий набор раздела). Параметр `site=1` — «Приём у себя».
  Кассы — `features.data.kupot` → `listings.kupot`; доставка/выезд/онлайн бизнесов — `features.data.formats` →
  `listings.formats` (вместе с «Зоной выезда»). Поля в редакторе с `when` видны только в подходящих категориях.
  Из `site_settings.amenities` убраны «Выезд на дом», «Онлайн» и кассы. Вариант В (особенности по категориям) — этап 5.
- Вход через Telegram (`src/lib/auth/telegram-session.ts`): подпись проверяется на сервере, пользователь Supabase
  создаётся со служебным адресом `tg-<id>@telegram.invalid`, сессия — через `generateLink` + `verifyOtp`.
  Supabase записывает `app_metadata` **после** вставки пользователя — поэтому есть триггер на обновление и явная запись в коде.
- Привязка: одноразовые токены `link_tokens` (10 минут). «Открыть в Telegram» → `t.me/haifabcbot?startapp=link_<token>`.
  «Привязать Google» → cookie + вход Google → `merge_profiles`.

## Проверка в песочнице без интернета

Песочница может не видеть Supabase, Vercel и Google Fonts. Проверочная сборка с подменой базы (второй аргумент —
миграция с примерными карточками, тогда собираются и их страницы, а `/k/demo1`…`/k/demo5` ведут на них):

```bash
python3 -I scripts/supabase-stub.py supabase/migrations/20261101000002_seed_dictionaries.sql \
  supabase/migrations/20261102000007_card_blocks.sql &
NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321 npm run build
NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321 npx next start -p 3100
```

Заглушка понимает и этап 5: берёт «Особенности» и тексты категорий из миграций 0015 и 0018 и отвечает на
`category_amenity_counts` (у примеров в заглушке нет подкатегорий, поэтому чипы видны на `/biznes`, а не на `/biznes/eda`).
Доступность проверялась axe-core через playwright-core с системным Chrome (`/usr/bin/google-chrome`), разовым скриптом.

Редактор без входа можно посмотреть локально: временная страница с `<ListingEditor>` и данными из миграции примеров
(не коммитить) + Playwright на 375/320 px. Живой сайт смотреть встроенным браузером приложения Claude. Перед `npx tsc --noEmit` выполнить `npx next typegen`.
Если окно Claude у заказчика в фоне, скриншоты встроенного браузера «застывают» — проверять вёрстку через JS
(`scrollWidth`, `getBoundingClientRect`), ширина телефона — `resize_window` 375 и 320. Фото Unsplash проверять загрузкой
`new Image()` в браузере: из песочницы images.unsplash.com недоступен.
